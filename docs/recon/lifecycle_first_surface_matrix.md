# Lifecycle-First Surface Matrix Recon

Surface: internal / recon
Retrieved: 2026-04-29
Target date: state of the world as of 2026-04-28

This is reconnaissance, not architecture. It maps what each host surface
appears to expose for a lifecycle-first Cortex wrapper. It must not be
read as a redesign plan or as live proof that Cortex improves model
output on any surface.

Legend:

- Mechanism strength: `full wrap` = Cortex owns the model call;
  `partial influence` = Cortex can inject or gate some context but not
  the host's hidden scaffolding; `observation-only` = Cortex can see or
  validate activity but cannot shape the call; `none` = no public
  extension path found.
- Fit marks: `natural fit`, `downgraded fit`, `doesn't port`.
- Source metadata is in [Sources](#sources). Docs without explicit
  last-updated metadata are flagged in
  [Stale or Missing Documentation](#stale-or-missing-documentation).

## Recent-change Notes

- Codex hooks are materially stronger than prior repo assumptions:
  Codex `Stop` hooks expose `last_assistant_message`, support
  `decision: "block"`, and convert the reason into a continuation prompt
  [S3]. This changes Codex App/CLI from doctrine-only to hook-enforceable
  when trusted project hooks are loaded.
- Gemini CLI has recent hook documentation with lifecycle events such as
  `BeforeAgent`, `BeforeModel`, `AfterModel`, and `AfterAgent`, and
  recent MCP / extension docs that make Gemini CLI more lifecycle-shaped
  than older assumptions implied [S19], [S18], [S20].
- Claude Code Desktop docs now state that project `CLAUDE.md`,
  `.mcp.json`/`~/.claude.json` MCP servers, hooks, skills, and settings
  apply to both CLI and Desktop Code sessions; Claude Desktop chat MCP
  config remains separate [S11].

## Nine-Cell Matrix

### OpenAI: API (Responses)

**Extension surfaces.** The Responses API exposes direct request control:
`input`, `instructions`, `tools`, `previous_response_id`, metadata,
background mode, and hosted / function tools [S1]. OpenAI docs also
separate API tool concepts and MCP/connectors from Codex-specific MCP
configuration [S1], [S4].

**Mechanism strength.** `full wrap`. Cortex can own both model-visible
instructions and input when it is the API caller. The current OpenAI
host-control bridge is strongest here because the shaped request body can
be captured deterministically before transport.

**Lifecycle-first fit.** task-local continuity: natural fit via
conversation state / previous response; interruption and resume: natural
fit if Cortex owns state; uncertainty brake: natural fit through
instructions / routing / retry policy; tool/host affordance routing:
natural fit through tools and hosted-tool choice; verified-work
preservation: natural fit because Cortex can place the work contract in
instructions/input; explicit closure: natural fit; capability envelope
detection: natural fit structurally, live fit still needs eval; runtime
context injection from feedback windows: natural fit through
`instructions` or bounded `input` context [S1].

**Pros / cons.** Pros: maximum request-body control, easiest deterministic
testing, strongest verified-work preservation. Cons: paid API surface,
not subscription-CLI dogfood, and less direct evidence about what happens
inside vendor agent scaffolding such as Codex CLI/App.

### OpenAI: Codex CLI

**Extension surfaces.** Codex CLI exposes terminal / non-interactive use,
project instructions via `AGENTS.md`, config files, hooks, MCP servers,
plugins, skills, slash commands, subagents, and an app-server surface in
the Codex docs navigation [S2], [S3], [S4]. Hooks include `Stop` with
`last_assistant_message`, `stop_hook_active`, and block/continue
semantics [S3]. MCP configuration can live in `~/.codex/config.toml` or a
trusted project `.codex/config.toml`, and the CLI / IDE extension share
MCP config [S4].

**Mechanism strength.** `partial influence`. Cortex can inject developer
context through hooks, shape project instructions, validate final output,
and expose tools via MCP, but it does not own the hidden Codex system
prompt or the exact final API request generated by the CLI.

**Lifecycle-first fit.** task-local continuity: natural fit inside a
Codex session, downgraded across sessions unless encoded in files/hooks;
interruption and resume: natural fit through CLI session mechanics but
not Cortex-owned; uncertainty brake: downgraded fit via hooks and prompt
context; tool/host affordance routing: natural fit through MCP / tool
policy, but host-owned; verified-work preservation: downgraded fit via
prompt/output contracts and workspace evidence, not full request control;
explicit closure: natural fit with Stop hook validation; capability
envelope detection: downgraded fit through observed CLI behavior; runtime
context injection from feedback windows: downgraded fit unless injected by
hook/prompt wrapper, because current product bridge reaches API
host-control rather than CLI scaffolding [S3], [S4].

**Pros / cons.** Pros: subscription auth, real repo agent surface, hooks
now provide a plausible hard gate for closure. Cons: hidden scaffolding,
harder to prove model-visible placement, and project trust / feature
flags must be empirically verified on the actual machine.

### OpenAI: Codex App for Mac

**Extension surfaces.** The Codex App docs describe local/worktree/cloud
threads, built-in Git operations, integrated terminal, worktree support,
slash commands, `/mcp`, skills, and app features such as in-app browser
and computer use in docs navigation [S5], [S6]. Codex hook and MCP docs
are not app-only, but project `.codex/config.toml` and trusted project
semantics are the relevant candidate path for app enforcement [S3], [S4].

**Mechanism strength.** `partial influence` when trusted project hooks
load; otherwise `observation-only` / doctrine. Cortex can validate final
messages via Codex Stop hook if the app honors the same project hook
config. Cortex cannot currently prove from public docs alone that every
app thread's hidden prompt stack is identical to CLI.

**Lifecycle-first fit.** task-local continuity: natural fit within app
threads; interruption and resume: natural fit through app sessions and
worktrees; uncertainty brake: downgraded fit through Stop/UserPrompt
hooks if loaded; tool/host affordance routing: downgraded fit through
MCP, terminal, app browser, computer use; verified-work preservation:
downgraded fit through output validation and diffs, not full model-call
control; explicit closure: natural fit if Stop hooks are active;
capability envelope detection: downgraded fit by observing app behavior;
runtime context injection: downgraded fit via hooks, not product
host-control [S3], [S5], [S6].

**Pros / cons.** Pros: best day-to-day dogfood surface for this repo,
worktree isolation, terminal visibility, visible diffs. Cons: public docs
do not expose the full model-call boundary; hook loading in app mode must
be verified with a local hook-health probe.

### Anthropic: API (Messages)

**Extension surfaces.** The Messages API exposes structured message
lists, top-level `system` rather than a `system` role, tools, server
tools, files, prompt caching, context management, and MCP connector
support through `mcp_servers` plus MCP toolsets [S7], [S8]. Anthropic's
MCP connector currently requires a beta header and supports remote HTTP
MCP servers, not local STDIO directly through the API [S8].

**Mechanism strength.** `full wrap`. Cortex can own `system`, messages,
tool definitions, and remote MCP server configuration when it is the API
caller.

**Lifecycle-first fit.** task-local continuity: natural fit through
message history / context management; interruption and resume: natural
fit if Cortex owns state; uncertainty brake: natural fit in system /
messages and tool loop; tool/host affordance routing: natural fit through
tools and MCP connector, with local-STDIO limitation; verified-work
preservation: natural fit; explicit closure: natural fit; capability
envelope detection: natural fit structurally; runtime context injection:
natural fit through `system` or bounded message context [S7], [S8].

**Pros / cons.** Pros: clean system-message control and tool loop,
official MCP connector. Cons: paid API, MCP connector limits, and no
direct answer about Claude Code/Desktop hidden scaffolding.

### Anthropic: Claude Code CLI

**Extension surfaces.** Claude Code exposes project and user settings,
hooks in `.claude/settings.json` / `.claude/settings.local.json`, Stop
hook transcript access, block decisions, MCP servers in `.mcp.json` or
`~/.claude.json`, project memory through `CLAUDE.md`, custom commands,
skills, plugins, and permissions [S9], [S10].

**Mechanism strength.** `partial influence`. Cortex can validate and
continue turns through hooks and can add tools/context through MCP and
files, but Claude Code's own system scaffold remains host-owned.

**Lifecycle-first fit.** task-local continuity: natural fit inside a
session; interruption and resume: natural fit through Claude Code session
mechanics; uncertainty brake: downgraded fit through hooks / MCP /
project instructions; tool/host affordance routing: natural fit through
MCP and permissions, host-owned; verified-work preservation: downgraded
fit via contracts, diffs, hooks; explicit closure: natural fit via Stop
hook; capability envelope detection: downgraded fit from observed
behavior; runtime context injection: downgraded fit unless a hook or
prompt wrapper inserts it into the turn [S9], [S10].

**Pros / cons.** Pros: strong lifecycle hooks and mature repo-agent
affordances. Cons: hidden prompt hierarchy, transcript parsing required
for Stop validation, and Desktop/chat MCP config divergence can confuse
handoffs.

### Anthropic: Claude Code App for Mac

**Extension surfaces.** Claude Code Desktop's Code tab supports local,
remote, and SSH sessions; diff review; embedded preview; integrated
terminal; file editor; connectors; computer use; skills; plugins; and
shared project configuration with CLI for `CLAUDE.md`, hooks, settings,
and `.mcp.json` / `~/.claude.json` MCP servers [S11]. Claude Desktop
chat extensions are separate: the desktop chat app uses Desktop
Extensions / MCP bundles and its chat MCP config is not the Code tab's
Claude Code MCP config [S11], [S12], [S13].

**Mechanism strength.** `partial influence` in the Code tab when the
shared Claude Code hook/settings model is active. For the ordinary
Claude Desktop chat app, mechanism strength is `partial influence`
through MCP/desktop extensions but not Claude Code hooks.

**Lifecycle-first fit.** task-local continuity: natural fit in Code-tab
sessions; interruption and resume: natural fit; uncertainty brake:
downgraded fit through hooks and Desktop session controls; tool/host
affordance routing: natural fit via MCP/connectors/computer use but
host-owned; verified-work preservation: downgraded fit via diffs/review
and hooks; explicit closure: natural fit if Code-tab hooks load;
capability envelope detection: downgraded fit; runtime context injection:
downgraded fit through hooks or prompt context, not full API control
[S11], [S12].

**Pros / cons.** Pros: app-level visibility, diff review, terminal,
parallel sessions, and shared CLI/Desktop Code configuration. Cons:
"Claude Desktop" and "Claude Code Desktop" are distinct enough that MCP
config can diverge; empirical verification must identify which tab/app is
being tested.

### Google: API (Gemini)

**Extension surfaces.** Gemini API exposes `contents`,
`systemInstruction`, generation config, thinking configuration,
function-calling tools, tool modes, built-in tools such as Search / code
execution / URL context, Files API, and SDK-level MCP tool use in the
function-calling flow [S14], [S15], [S16].

**Mechanism strength.** `full wrap`. Cortex can own the request contents,
system instruction, tool declarations, and file references when it calls
the API directly.

**Lifecycle-first fit.** task-local continuity: natural fit if Cortex
owns the chat/session; interruption and resume: natural fit if Cortex
owns state; uncertainty brake: natural fit via systemInstruction /
request policy; tool/host affordance routing: natural fit through
function declarations and built-in tools; verified-work preservation:
natural fit; explicit closure: natural fit; capability envelope
detection: natural fit structurally; runtime context injection: natural
fit via `systemInstruction` or `contents` [S14], [S15].

**Pros / cons.** Pros: clean request control and portable system
instruction shape. Cons: paid API, model/tool behavior variability, and
Gemini CLI/app behavior is not implied by API behavior.

### Google: Gemini CLI

**Extension surfaces.** Gemini CLI exposes `GEMINI.md` hierarchical
context files, `/memory`, custom context filenames, MCP servers in
`.gemini/settings.json` / `~/.gemini/settings.json`, hooks such as
`BeforeAgent`, `BeforeModel`, `AfterModel`, `AfterAgent`, custom
extensions, skills, commands, and built-in tools [S17], [S18], [S19],
[S20].

**Mechanism strength.** `partial influence`. `BeforeModel` is unusually
strong for an external lifecycle hook because it sits immediately before
LLM request dispatch, but Cortex still does not own the CLI's complete
host scaffold unless the hook API exposes and permits editing all
required request fields.

**Lifecycle-first fit.** task-local continuity: natural fit through
session plus `GEMINI.md`; interruption and resume: downgraded fit unless
captured in session/files; uncertainty brake: downgraded-to-natural fit
depending on hook event used; tool/host affordance routing: natural fit
through MCP and `BeforeToolSelection`; verified-work preservation:
downgraded fit through prompt/contracts/hooks; explicit closure: natural
fit with `AfterAgent`/`SessionEnd` hooks; capability envelope detection:
downgraded fit from observed behavior; runtime context injection:
downgraded-to-natural fit if `BeforeModel` can modify the request
payload, otherwise prompt/context-file injection only [S17], [S19].

**Pros / cons.** Pros: broad lifecycle hooks, MCP, and extension
packaging; potentially strong pre-model interception. Cons: official docs
are younger and need machine verification; request-mutation semantics
must be tested before claiming model-visible control.

### Google: Gemini App for Mac

**Extension surfaces.** Google documents Gemini for Mac as a native app
with global shortcuts, window sharing for contextual help, file/tool
attachment UI, cross-device chat history/memory sync, and Accessibility
permission for reading full browser pages [S21]. Gemini Apps Help
documents file upload, Drive / NotebookLM integration, charts, and
uploaded-code-folder / GitHub repository limits [S22]. No public official
hook, MCP-server, plugin, or custom-system-prompt surface was found for
Gemini App for Mac.

**Mechanism strength.** `none` for documented external lifecycle
control; `observation-only` if a separate process uses macOS
Accessibility/screen observation, which is not a documented Gemini
extension API.

**Lifecycle-first fit.** task-local continuity: downgraded fit through
app chat history only; interruption and resume: downgraded fit through UI
session; uncertainty brake: doesn't port as an external mechanism;
tool/host affordance routing: doesn't port except user-facing file/tool
UI; verified-work preservation: doesn't port beyond manually uploaded
artifacts; explicit closure: doesn't port; capability envelope detection:
observation-only; runtime context injection: doesn't port unless typed
manually or through unsupported UI automation [S21], [S22].

**Pros / cons.** Pros: broad consumer availability, screen/window context,
low-friction manual use. Cons: no documented lifecycle hooks or MCP; any
Cortex external influence would be brittle UI automation rather than a
supportable host adapter.

## Cross-Cutting Answers

### Where Verified-Work Preservation Survives

Verified-work preservation is strongest on the three API cells because
Cortex can place the contract in model-visible instructions/input and
capture the transport body: OpenAI Responses, Anthropic Messages, and
Gemini API [S1], [S7], [S14]. It is weaker but still useful on Codex
CLI/App, Claude Code CLI/Desktop Code, and Gemini CLI because hooks,
project context files, diffs, and final-output validators can enforce the
workflow but cannot prove ownership of the entire hidden model prompt
[S3], [S9], [S11], [S19]. It does not port cleanly to Gemini App for Mac
without unsupported UI automation [S21], [S22].

### CLI / App Relationships

OpenAI: Codex CLI and Codex App share the Codex documentation family, but
public docs make the CLI/IDE MCP sharing explicit while app hook loading
still needs local trust verification [S4], [S5]. Anthropic: Claude Code
CLI and Claude Code Desktop Code tab explicitly share `CLAUDE.md`,
hooks, skills, settings, and `.mcp.json`/`~/.claude.json` MCP servers;
Claude Desktop chat MCP config is separate [S11]. Google: Gemini CLI is
richly extensible; Gemini App for Mac is a consumer app with file/window
context and no documented hook/MCP parity [S17], [S21].

### MCP Convergence

MCP is clearly converging on developer-agent surfaces: Codex supports
MCP in CLI/IDE via `config.toml` [S4], Claude API and Claude Code support
MCP through API connector and local/project/user config [S8], [S10], and
Gemini CLI supports MCP servers in settings with multiple transports
[S18]. MCP is uneven on consumer app surfaces: Claude Desktop chat has
desktop extensions / MCP bundles [S12], Codex App likely inherits project
Codex config but needs empirical proof, and Gemini App for Mac has no
documented MCP surface [S21].

### Realistic Shape of Cortex as an External Process

For API cells, Cortex should remain the caller: host-control wrappers are
the least fragile shape. For CLI/app agent surfaces, Cortex is an
external influencer: project instruction file, lifecycle hook, MCP server,
or validator. Hooks provide the strongest lifecycle leverage when they
can inspect or modify the turn (`Stop` on Codex/Claude, `BeforeModel` on
Gemini CLI) [S3], [S9], [S19]. MCP is the best cross-host tool/context
bridge, but it is not automatically a closure/brake mechanism. File
watchers and Accessibility automation are lower-confidence fallbacks and
should be treated as empirical probes, not architecture.

## Questions Requiring Empirical Verification

- Codex App for Mac: prove trusted project `.codex/config.toml` loads
  Stop hooks in app threads and that `last_assistant_message` contains
  the final assistant text.
- Codex CLI/App: verify whether hook-provided `additionalContext` reaches
  the hidden model prompt in the same way across CLI and App.
- Claude Code Desktop: verify the Code tab loads the repo Stop hook from
  `.claude/settings.json` in local, worktree, and remote sessions.
- Claude Desktop chat: verify how Desktop Extensions / MCP bundles expose
  tool descriptions and whether any hook-like turn boundary exists
  outside Code tab.
- Gemini CLI: verify whether `BeforeModel` can mutate the actual request
  body or only observe / block / add context; this is decisive for
  runtime-context injection.
- Gemini App for Mac: verify no hidden developer extension surface exists
  beyond file/window sharing and Accessibility-assisted observation.
- All CLI/app surfaces: run a controlled "sentinel string" test to prove
  whether injected runtime context survives vendor scaffolding and appears
  in model-visible context.

## Stale or Missing Documentation

- OpenAI Codex docs currently expose the relevant hook/App/MCP surfaces,
  but the pages inspected here did not show explicit last-updated dates;
  treat Codex lifecycle claims as current-source-backed but requiring
  routine recheck [S2], [S3], [S4], [S5].
- Anthropic API pages are partly dynamic and some API reference content
  loaded sparsely through the browser; the MCP connector page is usable
  and names a beta header, but exact last-updated metadata was not visible
  [S7], [S8].
- Anthropic Desktop Extension engineering post is older than six months
  by target date, but the Claude Desktop install/help source says Desktop
  Extensions are current and was updated this week [S12], [S13].
- Gemini CLI docs include recent published/last-updated metadata in search
  snippets for hooks, MCP, and context files; keep them on a short recheck
  interval because the hook system is new [S17], [S18], [S19].
- Gemini App for Mac documentation is product/help documentation, not a
  developer extension reference. The absence of hook/MCP docs is itself a
  finding, not proof that no internal/private integration exists [S21],
  [S22].
