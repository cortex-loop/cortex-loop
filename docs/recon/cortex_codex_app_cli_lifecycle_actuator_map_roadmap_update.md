# Codex App/CLI Lifecycle Actuator Map Roadmap Update

Surface: product architecture + doctrine/status

## Summary

The task-standard roadmap is paused before another live behavior comparison.
The scored-lexical offline-readiness work remains valid and should be
published, but the next product question is no longer Sinkhorn or a live
three-arm rerun. The next question is whether Codex App/CLI is using Cortex's
lifecycle surfaces as real executive actuators rather than as Stop-first state
capture.

The current Codex App/CLI product bridge reaches the model primarily through
the signed UserPromptSubmit task-set context and late Stop continuation text.
PreToolUse, PostToolUse, and failure events currently function mostly as
perception and state update. That is not enough to claim lifecycle-first
product effect.

## Actuator Map

- SessionStart: session and workspace context only.
- UserPromptSubmit: prospective task-set formation.
- PreToolUse: hard motor deny/block only; do not treat it as a coaching-text
  surface because Codex does not support additionalContext there.
- PermissionRequest: approval-bound route control.
- PostToolUse: strongest near-term next-step correction surface because it can
  replace or annotate tool feedback before the next model step.
- Stop: late closure continuation.

## Roadmap Decision

1. Publish the current offline-readiness branch so dirty branch state does not
   confuse architecture decisions.
2. Pause live task-standard behavior comparisons.
3. Defer Sinkhorn and transport calibration until the actuator loop exists and
   evidence allocation precision is still load-bearing.
4. Build a Codex App/CLI lifecycle actuator map as the next doctrine/status
   seam.
5. Queue PostToolUse task-standard/expectation next-step correction as the
   next implementation seam.
6. Probe PreToolUse motor inhibition after PostToolUse, treating it as
   action blocking rather than model coaching.
